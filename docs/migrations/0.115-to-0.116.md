# 0.115 → 0.116 — `!must_fill` is gone; a `~~~` block with no `$kind` is a code block; a card of an undeclared kind, and a body under `body.enabled: false`, render and warn; an undeclared key warns; a non-mapping root payload fails at its fence

The break nothing reports first: **a value under `!must_fill` is dropped on
load.** A stored row or a markdown document carrying the marker loads with
that field unanswered, the example text under it gone, where it loaded the
text as a placeholder. See [`!must_fill` is removed](#must_fill-is-removed).

The break nothing reports: **a document that failed to render now renders.**
A card whose `$kind` the quill does not declare, and body prose under
`body.enabled: false`, were fatal `validation::*` errors. Each is now a
`Warning` from `quill.validate(doc)`, and the render proceeds without the
input. A pipeline that relied on the render failing to catch these documents
catches nothing: run `quill.validate(doc)` and act on the two codes below. On
the CLI, `render` prints them, and `quillmark check --strict` fails on them.

A `~~~` block after the root that names no `$kind` parsed as a card with no
kind, and failed validation. It is no card now: no schema can claim a block
that names no kind. It renders as a code block in the body above, the prose
after it stays in that body, and the parse warns `parse::missing_kind` at its
fence. A block whose YAML does not parse still fails, whatever its info
string.

The rule behind it: a render fails only where the engine would have to invent
what the author wrote. Input no declaration claims displaces nothing, so it
renders and warns
([SCHEMAS.md § What blocks a render](https://github.com/borb-sh/quillmark/blob/main/prose/canon/SCHEMAS.md#what-blocks-a-render)).

## `!must_fill` is removed

The marker said a cell held a placeholder rather than an answer, and the
schema half of `validation::must_fill` said a cell with no `default:` needed
one. Neither survives: `default:` is the value an unanswered cell renders and
nothing more, `?` moves the render floor and nothing more, and null ≡ absent
holds on every surface — `field: ""` and `field: null` differ in the value they
render and in nothing else.

**What loads.** A value the marker held was the schema's example, not an
answer, so every reader drops it with the marker:

| Stored as | Loads as |
|---|---|
| `subject: !must_fill Example` | `subject:` (null) |
| `recipient: !must_fill` over a block sequence | `recipient:` (null) |
| `addr:` with `street: !must_fill Main` beneath it | `addr: {street: null, …}` |
| a stored row's field with `"fill": true` | the field, value null |
| a stored row's `nested_fills` path | that node, null |
| `$ext`/`$seed` content tagged `!must_fill X` | `X`, tag dropped |

The markdown reader warns `parse::unsupported_yaml_tag` at each path it drops.
A row whose placeholder was later overwritten in raw markdown without removing
the tag loses that value too: re-author it.

**What seeding makes.** A seed is a document nobody has answered: one card per
declared kind, each with its `body.example`, every field absent and rendering
its `default:` or blank. An `example:` shows in the blueprint's `# e.g.` line
and nowhere else. `seed_card` commits the document's `$seed` overlay for the
kind, taken whole, over that.

```yaml
# 0.115 blueprint
recipient: !must_fill # array<string>
  - Mr. John Doe

# 0.116 blueprint
# e.g. [Mr. John Doe]
recipient: # array<string>
```

## The render date

A document dated by the day it renders stores `today` in a `date` field, or its
quill declares `default: today`. The engine reads no clock: the host passes the
render date, and the field and a plate's `datetime.today()` both render as it.

```rust
let today: CalendarDate = "2026-03-14".parse()?;
let session = engine.open(&quill, &doc, Some(today))?;
```

The CLI takes `--today YYYY-MM-DD`; `engine.open` / `engine.render` /
`reader.resolve` take an optional trailing `YYYY-MM-DD` string in JavaScript,
and `engine.render` a `today=` `datetime.date` in Python. Each defaults to the
local date.

## What reaches the plate

A card no kind claims keeps its place in `$cards` with its `$kind` as
authored, its fields verbatim and uncoerced, and no `$body`. A plate that
branches on the kinds it knows falls through on it, which is what every
fixture plate does. Every card carries `$kind`, so a bare `card.at("$kind")`
reads.

A body under `body.enabled: false` does not reach the plate, as before.

## An undeclared key warns

`quill.validate(doc)` warns `validation::unknown_field` at each key the schema
does not declare where it sits: a card field, a typed dictionary's property, an
array element's property, a matrix member's column, or a cell inside a variant
container that no world declares. The render is unchanged: the key still
crosses to the plate verbatim, except inside a variant container, whose wire
carries only the live world.

A strict consumer that reads an empty `validate` as done sees the new warning
on any document carrying such a key. That includes a key a plate reads through
`data.at("logo", default: none)` without declaring it: declare it in
`Quill.yaml`, and the warning goes.

The hint names the likely fix, and `args` carry it. `container` and `variant`
mark a variant cell written beside its discriminant (`outcome: motion` with
`moved_by:` next to it rather than under it). `suggestion` names the declared
field a misspelled key most likely meant.

## A non-mapping root payload has its own code

A document's first `~~~` block is its root whatever it holds, so a document
opening with tilde-fenced code reaches the YAML parser, where the code usually
reads as a string. It failed as `parse::missing_quill`, which named neither
rule nor fix. It is now its own code, located at the opener's line, and its
hint names the backtick fence to write instead.

| A block holding | 0.115 | 0.116 |
|---|---|---|
| a string, number, boolean or sequence, as the root | `parse::missing_quill` | `parse::payload_not_mapping`, located at the opener |
| the same, after the root | `parse::invalid_structure`, `Invalid YAML in card block: expected a mapping`, no location | a code block; `parse::missing_kind` warns |
| a mapping with no `$kind`, after the root | a card with no kind; the render fails | a code block; `parse::missing_kind` warns |
| YAML that does not parse, whatever the info string | `parse::yaml_error_with_location` | unchanged |

`args` carries `actual` (`string`, `number`, `boolean` or `sequence`) and, when
the opener has an info string, `info`: `python` for `~~~python`.

**Migrate:** a consumer routing the non-mapping root under
`parse::missing_quill` routes it under `parse::payload_not_mapping`. To fix a
document, open it with the `~~~` root block and fence code with backticks.

## `paint` takes one scale

`paint` rasterized at `layoutScale × densityScale` and reported
`layoutWidth = widthPt × layoutScale` back, a number the caller computed to
pass in. It takes the product alone, backing-store pixels per point, as a
required argument, and returns `undefined`.

```ts
// 0.115
const r = session.paint(ctx, page, { layoutScale, densityScale });
canvas.style.width = `${r.layoutWidth}px`;
canvas.style.height = `${r.layoutHeight}px`;

// 0.116
session.paint(ctx, page, layoutScale * densityScale);
canvas.style.width = `${widthPt * layoutScale}px`; // or "100%" of a page box
canvas.style.height = `${heightPt * layoutScale}px`;
```

A call with no scale, or with an options object, throws
`backend::invalid_raster_scale` where the first painted at 1 and the second at
the options' product. A scale that is not finite and positive throws the same
code, where it threw an uncoded message.

The painter still reduces a scale that would put a side past 16384 px. A
consumer that read `clamped`, `effectiveDensityScale` or `pixelWidth` /
`pixelHeight` reads `canvas.width` / `canvas.height`, and the scale painted at
is `canvas.width / widthPt`.

## One raster ceiling

Core refused a raster past 16384² px of area (`MAX_RASTER_PIXELS`) and the
WASM painter clamped at 16384 px a side, a limit of its own. The side is the
one limit now, core's `MAX_RASTER_SIDE`, and `fit_raster_scale` is the
reduction `paint` applies. The side rule is the narrower of the two only for a
page long on one axis: a PNG export whose long side passes 16384 px at the
asked `ppi` fails under `backend::invalid_raster_scale`, where it rendered
while its area fit.
